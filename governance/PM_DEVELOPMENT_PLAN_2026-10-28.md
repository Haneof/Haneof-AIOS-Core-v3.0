## 2. S0 — 恢复可测

### T1 跨平台文件锁

- **问题**：`resilient_handler.py:44` 硬 `import fcntl`，Windows 上模块导入失败 → `pytest tests` 收集即死，生产模型路径在开发平台不可用。
- **改法**：抽出 `src/aios_core/runtime/_filelock.py`，两个实现：
  - POSIX：`fcntl.flock`
  - Windows：`msvcrt.locking`（或 `LockFileEx` via ctypes）
  - 对外只暴露 `exclusive(path)` 上下文管理器。
- **验收**：
  1. Windows 上 `python -c "import aios_core.runtime.resilient_handler"` 成功；
  2. `pytest tests --collect-only` 在 Windows 上通过；
  3. Linux CI 保持绿。
- **反向验证（必做）**：两个进程同时抢同一把锁，写同一个文件 100 次，最终计数必须正好 100。回退实现若退化成空操作，这条会红。

### T2 统一检查入口

- **改法**：`tools/check.py` —— 跑全量测试、跑治理基线、打印跳过原因分布与耗时。
- **验收**：一条命令给出 PASS/FAIL 与耗时。本地跑完的耗时本身要记录（10-26 是 16m50s，10-28 超过 49 分钟还没结束，需要先看是谁在等）。

## 3. S1 — 把延迟降回来

这一节是当前唯一的产品级阻塞。**在 M4 达标之前，不加任何新能力。**

### T3 热集：只广告该广告的能力

- **问题**：`_build_native_tools(snapshot.capability_catalog)` 把 53 个能力全量翻译成 JSON Schema，逐轮发送，34,736 字符（≈11.5k token）。
- **改法**：分三档，实测取拐点。
  - 热集（默认 12–15 个）：连续性写 7 个 + 每轮必需的读 5–8 个
  - 冷集：留在提示词名单里，不给 schema；需要时用 `describe_capability(name)` 现取
- **验收**：tools payload ≤ 8,000 字符；对话轮中位 ≤ 40s；M1 不降（仍 ≥90%）。
- **注意**：这一条会改变模型能看到的能力面，属产品决策，见第 6 节。

### T4 抽取轮延后执行

- **问题**：抽取在 `run_turn` 里同步跑，用户要等它。中位 73.1s。
- **改法**：回复先落库并返回，抽取放到后台任务；**下一轮开始前**必须完成（`run_turn` 入口处 await 上一轮的 pending extraction）。
- **验收**：
  1. 用户感知延迟 = 对话轮耗时（M4）；
  2. 第二场会话仍能复述（M2 = 100%）——因为跨会话前必有一次落库；
  3. 同一会话内连续两轮问"你记得吗"，第二轮允许读不到（这是**明确接受**的语义让步，见第 6 节）。

### T4b 抽取条件触发

- **改法**：本轮是否"用户自我陈述"用启发式判定（第一人称 + 我是/我在/我做/我叫/我习惯/我住/我在做…），未命中则跳过抽取调用。
- **验收**：12 轮混合对话（含闲聊、提问、事实陈述）里，抽取调用数 ≤ 命中轮次数；**该抽未抽 ≤ 10%**（用人工标注的 12 轮做基准）。
- **顺序**：T4b 可以晚于 T4；T4 是结构性收益，T4b 是额外省调用。

### T5 模型能力探测

- **问题**：T10 报告在一个模型（`minimax-m3.1-flash`）、一次运行上得出"原生 tools 是正解"；同一份代码在 `grok-4.6` 上 **0/6** 次工具调用。
- **改法**：`tools/model_probe.py`，对任意端点跑 n=6 的"给定 tools 会不会调用写入能力"，输出：
  ```
  endpoint=... model=... tools_call_rate=0/6 -> 该模型不能承担主写入路径，抽取轮必须开
  ```
- **验收**：对 grok-4.6 与 minimax 各跑一次，结论与实测一致；把结论写进 `docs/operations/LOCAL_MODEL.md`。
- **意义**：把"某个模型行不行"变成可重复的判定，而不是一次性的好消息。

## 4. S2 — 凭证与证据

### T6 轮换硬编码的 NVIDIA key（**owner 决策**）

- **现状**：`src/aios_core/runtime/resilient_handler.py:70` 有真实 key，仓库 public，已在 git 历史里；治理用 `secret_allowlist` 显式放行。
- **改法**：
  1. 轮换 key（在 NVIDIA 控制台作废旧 key）；
  2. 代码只读 env，无默认值；缺 key 时 fail-closed（现在是"静默用默认值"）；
  3. 删掉 `secret_allowlist` 那条；
  4. CI 用 repository secret 注入。
- **验收**：`grep -rn "nvapi-" src/` 无输出；无 key 时抛明确错误而不是发请求；CI 绿。
- **代价**：旧 key 已公开，**轮换前它一直可用**。这不是"清理代码"，是止损。

- `reviews/AIOS_T10_NATIVE_TOOLS_VERIFICATION_2026-10-27.md` 顶部加状态块：`n=1 / 单模型 / 结论不普适`，并链接本次复审核的 6/6 + `calls_ok=0` 对照。

## 6. 需要 owner 拍的四件事

1. **T6 轮换 key** —— 公开仓库里的活凭证。我建议立刻轮换；不轮换的话，任何人 clone 都能花你的额度。
2. **T4 接受"回复先返回、记忆稍后落库"** —— 语义让步：同一会话内紧接着问"你记得吗"，可能读不到刚说的事（跨会话一定读得到）。这是拿一致性换延迟。
3. **T3 热集砍到 12–15 个能力** —— 决定模型能直接看到哪些能力。建议：7 个连续性写 + `list_dimensions` / `get_world_map` / `recall` 这类读，其余走 `describe_capability`。
4. **T4b 是否接受启发式漏判** —— 漏判 = 该记的没记。我设的容忍线是 10%。
