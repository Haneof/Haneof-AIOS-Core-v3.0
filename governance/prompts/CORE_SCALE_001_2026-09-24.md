All measurements must record:

### Tier S10K — interactive sanity

Dataset:
- 10,000 current Claim objects with realistic spread across AI-world domains/tags/status;
- enough Evidence/Dependency/revisions to exercise current-view filtering;
- representative search postings.

Hard budgets:
- `core_context` p95 <= 0.75 s
- `snapshot` p95 <= 1.5 s
- broad `recall_candidates(limit=20)` p95 <= 1.0 s
- no operation peak-RSS delta > 512 MiB
- no fixed top-k search may issue > 200 SQL statements

### Tier S100K — RC interactive envelope

Dataset:
- 100,000 current Claim objects with representative revisions/evidence/dependencies;
- at least 1,000,000 total mixed World revisions/objects may be included if generation cost is practical, but 100k current Claims is mandatory;
- realistic broad-token search hit distribution.

Hard budgets:
- `core_context` p95 <= 2.0 s
- `snapshot` p95 <= 5.0 s
- broad `recall_candidates(limit=20)` p95 <= 2.5 s
- peak RSS for each measured retrieval <= 1.5 GiB above steady baseline
- broad top-k recall SQL statements <= 500
- SQL count must not grow linearly with candidate hit count in an N+1 pattern

### Tier S1M — capacity safety envelope

Dataset:
- 1,000,000 current Claim objects, or an equivalent mechanically documented corpus that produces one million current Claim payloads in the same retrieval path.

Hard budgets:
- must complete construction and required retrieval probes under a 4 GiB process/cgroup memory envelope without OOM
- `core_context` p95 <= 10 s
- `snapshot` p95 <= 20 s
- broad `recall_candidates(limit=20)` p95 <= 10 s
- retrieval peak RSS <= 3.0 GiB
- fixed top-k recall SQL statements <= 1,000
- failure must be explicit if the environment cannot supply the declared 4 GiB envelope; do not silently reduce the corpus and call it PASS

The 1M tier is a capacity/safety gate, not a claim that all interactive latency should match the smaller tiers.

## Cold start / restart envelope

On S100K:
- clean process open of an already-current World+index: p95 <= 3 s
- open with a stale but valid index requiring catch-up: p95 <= 10 s
- world/index revision must remain correct
- startup must not eagerly deserialize the entire World into Python memory

On S1M:
- current World+index cold open must complete without OOM;
- record p50/p95 and RSS even if below the hard 10 s target is not required beyond the existing 20 s safety window;
- no hidden full-World Python materialization is allowed merely to open the Core.

## Due-work / backlog envelope

Use mechanical fake model handlers only.

Create a disposable backlog containing at least:
- 1,000 due Wake/Review/Summary-like mechanical due records across time windows, using the repository's real durable mechanisms where applicable.

Measure:
- due discovery latency;
- SQL count;
- RSS;
- bounded batch processing of 100 due mechanical items;
- remaining backlog count and ordering;
- restart with backlog intact.

Hard budgets:
- due discovery p95 <= 2 s at 1,000 due items;
- bounded 100-item mechanical batch orchestration overhead <= 5 s excluding intentional model-handler sleep;
- no loss, duplication, or starvation caused by pagination/batching;
- backlog must remain durable across restart.

If a task requires actual model tokens/provider calls, report token/cost as UNKNOWN unless a real provider call was explicitly part of an existing safe mechanical benchmark. Do not invent cost.

## If a hard budget fails

First preserve a red benchmark/probe tied to an exact head.

Then make the smallest semantics-preserving repair.

Preferred classes of repair, only when proven necessary:
- SQL predicate/filter pushdown that preserves exact current/historical semantics;
- streaming/fetchmany instead of unbounded fetchall;
- batch lookup replacing N+1 queries;
- safe SQLite indexes;
- bounded pagination/candidate windows where output semantics are unchanged;
- bounded caches that are rebuildable/derivable and never truth.

Do not introduce:
- a vector DB as a second truth source;
- a new cognition store;
- a materialized cognition truth table that changes authority;
- approximate retrieval in place of exact required semantics;
- fixed domain/personality rules;
- semantic truncation just to hit latency;
- changed Claim/Evidence/Revision meaning;
- relaxed subject isolation;
- weakened FIX-001 historical cutoff;
- weakened FIX-002/003 recovery;
- async work that silently drops durable due items.

If an optimization requires a semantic/constitutional change, STOP and report PM.

## Semantic equivalence requirement

Any optimization of retrieval/query/index paths must be proven equivalent against the pre-optimization behavior on deterministic small/medium corpora.

At minimum compare:
- object ids/revisions returned;
- ordering where contractually meaningful;
- active/inactive filtering;
- subject isolation;
- knowledge cutoff / `as_of` behavior;
- revision selection;
- evidence/dependency visibility;
- exact `limit` behavior;
- search/index watermark behavior.

A faster wrong answer is a FAIL.

## Recovery compatibility

Because RECOVERY is now integrated:
- new indexes/schema additions must survive backup/restore correctly;
- index remains rebuildable from World;
- future-schema fail-closed remains valid;
- no optimization may require restoring cache as truth;
- new schema/index creation must be restart-safe/idempotent.

If schema version must change, STOP and report PM unless the change is strictly an additive SQLite index that does not alter World schema compatibility semantics.
