# AIOS v3.0 开发方案（PM，2026-10-26 初版 / 2026-10-27 修正）

> 依据：`reviews/AIOS_PM_REPO_AUDIT_2026-10-26.md`（含复测修正）。
> 这份方案只解决一件事：**让手环真的记得住人**。其他都排在它后面。
>
> **与初版的差别**：初版把"换成原生工具调用"当成主修。复测证明接口不是根因（A/B：原生 3/6 vs 文本 4/6），
> 主修改为**把写入变成结构性要求**，并**先造一把能重复测量的尺**——初版判错就是因为没有这把尺。

---

## 0. 目标定义（先定验收，再排任务）

当前产品状态一句话：**一轮对话结束后，世界上基本没有留下关于这个人的认知，而且这件事是随机的。**

验收看四个数。全部要求 n≥12，单次运行不算数。

| 编号 | 指标 | 现状（复测） | 目标 | 怎么测 |
|---|---|---|---|---|
| M1 | 含 durable 事实的单轮，durable claim 产出率 | **≈10%（2/19）**；端到端 n=6 实测 **0/6** | ≥ 90% | 独立会话 × 12，每个只含一条记忆价值陈述，读世界库 |
| M2 | 跨会话可复述率（**关掉逐字对话**） | 0 | 100% | `recent_turn_limit=0`，第二场会话答出姓名/城市/产品 |
| M3 | 重复陈述产生的重复 claim | 未测（写入率提高后必现） | 0 | 连续两轮问同一事实，claim 计数不增 |
| M4 | 单轮回复延迟 | 12.7–64.0s（本机网关，7 轮中位数 20.2s） | 不增加 | 同端点前后对比 |

M2 是唯一不能伪造的指标。M1 可以靠模型"演"，M2 不行——关掉逐字对话之后，它要么从身份锚里读到了，要么就是不知道。

M1 的现状必须写成区间（0%–65%），不能写成点估计。**这正是初版犯的错。**

## 1. 阶段划分

```text
S0 造尺（0.5 天）    把"写入率"变成一条能重复跑的命令 —— 没有它，后面每一步都在猜
   ↓
S1 止血（1 天）      让"仓库健康"变成一个能跑出结论的判断
   ↓
S2 提写入率（2–3 天）把写入从"建议"变成"必须做的决定"，同时保证写对格式
   ↓
S3 证明（1 天）      真实端点跑 M1–M4，落库取证
   ↓
S4 治理归位（0.5 天）记录回到与现实一致
```

顺序上有一处与初版不同：**S0 提到最前**。理由很直接——初版用一个样本下了根因结论，被复测推翻。没有可重复的度量，后面每一步都会重复这个错误。

## 2. S0 — 造尺

### T00 写入率测量工具

- **改法**：把 `exp_durable_rate.py` 的逻辑固化进 `tools/write_rate_probe.py`。
  - 参数：`--turns N`、`--model`、`--base-url`、`--api-key`、`--report`
  - 每个样本 = 独立 world + 单轮会话，内容固定为一条记忆价值陈述
  - 输出三件事：durable 数、未调用数、调用被拒数（含 `error_code`）
- **验收**：
  1. 同一份代码连跑两次，两次结果差异不超过 1 个样本（否则样本量不够，工具自己报"不可信"）；
  2. 报告里必须区分 `no-call` / `rejected:<error_code>` / `durable` 三类，否则无法判断该改内核还是改提示词；
  3. 默认 `--turns 12`。
- **反向验证**：把 `commit_ai_world_claim` 的 handler 改成恒失败，工具必须报 `rejected:` 而不是 `no-call`。

**这条不做完，S2 的任何结论都不许写进文档。**

## 3. S1 — 止血

### T01 让冻结校验不依赖换行符

- **问题**：`tests/c15_persistence/killpoints/test_killpoints.py` 对 `PROBE_MANIFEST.json` 的**原始字节**取 sha256。Windows 上文件被 CRLF 重写后哈希对不上，而 git 的 `eol=lf` 让 `git status` 看不见差异——文件"看起来没改"，测试却收集失败，**整个 `pytest tests` 直接挂掉**。
- **改法**：校验前把 `\r\n` 归一到 `\n` 再取哈希。
- **验收**：Windows 上 `pytest tests/c15_persistence` 能收集并通过。
- **反向验证（必做）**：改 manifest 里一个字符，测试必须变红。归一化不能把校验变空。

### T02 清理 CRLF 入库的两个测试文件

- **问题**：`tests/unit/test_m1_001r_adv_independent_redteam.py`、`tests/unit/test_m1_001r_high_entropy_audio.py` 的 blob 内含 CR（302 / 389 个），与 `.gitattributes` 的 `* text=auto eol=lf` 冲突，`git status` 永久显示 691 行假改动。
- **改法**：`git add --renormalize`。
- **验收**：`git status` 干净。

### T03 加一个统一检查入口

- **问题**：55 个 workflow 各跑子集，仓库里没有 Makefile / tox / nox / scripts。没有任何一条命令能回答"这个仓库现在是健康的吗"。
- **改法**：`tools/check.py`，三步：跑全量测试 → 跑治理基线校验 → 打印跳过原因分布。不引新依赖。
- **验收**：一条命令输出 PASS/FAIL 与耗时（全量基线 ≈ 17 分钟）。

### T04 并发 attach 的持久化不变量（**需 owner 定性**）

- **现象**：`test_ca2_015_concurrent_attach_yields_one_canonical_winner` 多次复现失败。两个线程同时 attach，其中一个抛 `sqlite3.OperationalError: attempt to write a readonly database`，被包成 `StoreError` 逃出 worker，测试只收到 1 个 outcome，断言 `['accepted'] != ['accepted','refused']` 失败。失败时线程还可能挂住。
- **为什么不能顺手改**：这正是 C15 的持久化不变量。要区分：
  - **测试写窄了**：worker 只捕获 `BackgroundModelResponseConflict`，`StoreError` 没算 outcome → 改测试。
  - **内核真漏了**：store 把一次可重试的并发写映射成不可重试的 `storage_unavailable`，语义上应映射成 `VERSION_CONFLICT` → 改 `sqlite_store`。
- **验收**：先给定性结论，再改；改完连跑 10 次全绿，且不出现挂起。

## 4. S2 — 提写入率（本方案的核心）

### 为什么是"结构性要求"而不是"更好的提示词"

复测数据：提示词从 3807 加到 5272 字符，调用率没有变化；换接口（原生 tools 3/6 vs 文本 4/6）也没有变化。**改变措辞和改变接口都不改变"要不要写"。**

剩下的解释只有一个：写入当前是**建议**。模型回答用户是默认行为、收益立刻可见；写入的收益在下一场会话才兑现，本轮看不见。默认行为永远赢。

所以要动的是**契约**，不是措辞。

### T05 输出契约里增加必填的 memory 决策（**契约变更，需 owner 拍**）

- **改法**：一次响应必须同时给出 `reply` 和 `memory`。`memory` **必填、允许空数组**。
  - 空是合法答案，模型不会为了填满它编造；
  - 但它必须对"这一轮有没有值得记的东西"表态。
- **为什么不是"允许"而是"必填"**：可选字段的省略成本是零，模型会省略。这条在初版里已经论证过，复测数据加强了这个判断（提示词里的建议从未生效）。
- **为什么不做独立抽取轮（方案 B）**：每轮固定 +1 次调用，本机 12–64 秒/轮，手环上延迟翻倍。只在 T05 上线后写入率仍 <60% 时作为兜底，且只在"用户本轮是自我陈述"的轮次触发（第一人称 + 我是/我在/我做/我叫/我习惯 的启发式，不引入第三次模型调用）。
- **验收**：`tools/write_rate_probe.py --turns 12` 写入率 ≥ 90%；回复延迟不增加（M4）。
- **反向验证**：把 `memory` 改回可选，写入率必须掉回去。不掉说明测试是空的。

### T06 原生工具调用（定位：提高写入质量，不是根因）

- **改法**：provider 新增 `stream_chat_with_tools()`，payload 加 `tools`；SSE delta 按 `index` 聚合 `tool_calls`（name 首帧给，arguments 分片拼接）。**旧的 `stream_chat` 签名不变**，避免一次改动打碎所有调用方和测试。
- **配套**：`input_schema` → JSON Schema 转换器（34 种类型串，表驱动），覆盖 `string` / `integer` / `number` / `boolean` / `array[T]` / `array[{object_id:string,revision:integer}]` / `{object_id:string,revision:integer}` / `number[0,1]` / `a|b|c`（→ enum）/ `object?` / `ISO-8601 datetime` / 尾缀 `?`。
- **为什么仍然要做**：复测里那 2/6 的调用**全部缺必填参数**（`evidence_refs`、`confidence`），被内核拒掉。`tools` 的 `required` 是模型侧会遵守的约束，比散文里的样例可靠。**这是把"尝试写"变成"写成"的那一步。**
- **验收**：
  1. loopback stub 造分片 `tool_calls`（arguments 拆 3 段），解析结果与预期一致；
  2. 53 个能力的生成 schema 全量断言：`required` 集合 == `required_arguments()` 结果；
  3. `tools/write_rate_probe.py` 的 `rejected:` 计数降到 0。

### T07 放宽 `ModelDirective` 不变量（**契约变更，需 owner 拍**）

- **现状**：`__post_init__` 硬性禁止 `capability_calls` 与 `response` 共存。这个不变量**没有任何测试覆盖**——不是被验证过的设计，只是当初随手加的一道门。
- **为什么必须改**：原生工具调用下模型会**一次响应里既写记忆又回答用户**（实测 T3：`commit_world_claim` + `reply_to_user` 同时出现）。
- **改法**：允许共存，并在回合循环里定规则：
  - 本批调用**全是写** → 执行，然后用 response 终止，**不多一轮**（省一次往返）；
  - 本批调用**含读** → 执行，回灌结果，再叫一轮（否则回复是在没看到读结果时编的）。
- **验收**：两条路径各一个测试；写路径断言 `model_rounds == 1`，读路径断言 `model_rounds == 2` 且第二轮能看到工具结果。

### T08 写入去重（**语义变更，需 owner 拍**）

- **问题**：`_commit_ai_world_claim` 与 `ai_world.commit` 都没有内容级去重。实测模型会把同一事实原样重写（T4 四连写）。
- **改法**：在 (domain, 归一化 statement, subject) 上做内容级去重，命中时返回 `duplicate: true` 而不新建 revision。
- **验收**：连续两轮陈述同一事实，claim 计数不增（M3）。
- **顺序**：**必须和 T05/T06 同批上线**。写入率一提高，重复就会立刻变成主要矛盾。

### T09 热集选择

- **问题**：53 个能力、28 个写路径。全给 schema 会挤占上下文并降低选择准确率。
- **改法**：advertise 12–15 个（7 个连续性写 + 必要的读），其余仍留在提示词名单里但不给 schema。
- **验收**：对比 12 / 25 / 53 三档的写入率、误调率与延迟，取拐点。**实测，不靠猜。**

## 8. 风险与回滚

| 风险 | 表现 | 处置 |
|---|---|---|
| T05 只让模型"表态"不写 | `memory` 恒为空数组，形式上合规 | 验收线第一条是写入率，不是"契约改完了"；同时统计"有 durable 内容但 memory 为空"的比例 |
| T06 schema 转换有偏差 | 模型稳定写错某个参数，看起来像"模型笨" | 53 项全量断言；错误必须落在内核而不是模型身上 |
| T07 放宽不变量后歧义 | 模型既调用又回复，用户看到重复内容 | 只对"全是写"的批次走快路径；含读一律回灌 |
| T08 去重过激 | 语义相近但不同的陈述被吞 | 只对归一化后完全相同的 statement 去重；近似交给模型判断 |
| 端点状态漂移 | 502 / 超时 / 模型可用性变化（本次已遇到 4.7 从 502 变 200） | 探针内置重试；结论只在完整跑完时才算数；端点状态写进报告 |
| **样本不足导致误判** | 初版就是这样判错的 | T00 强制 `--turns 12`；两次运行差 >1 个样本则工具自报"不可信" |

**回滚点**：T06 是纯新增方法，`stream_chat` 不动；T05/T07 用开关（`AIOS_OUTPUT_CONTRACT=envelope|legacy`）包住，出问题关开关即回到旧契约，内核其余部分不受影响。

## 9. 明确不做

1. **不再往提示词加字**。三轮实测证伪（3807→5272 字符，调用数无变化）。
2. **不为弱模型放宽证据语义**（裸 id 自动解析 revision）。测试台的缺陷不进产品。
3. **不跳过 T00 直接改**。没有可重复度量，改完只能靠感觉验收。
4. **不跳过 T08 直接提写入率**。写入率上来的第一天就会出现重复 claim。
5. **不在 S2 之前动 UI / 硬件 / Android**。契约要变，先变完再往上盖。
6. **不用单次运行或"最后一个回答对不对"判断连续性**。前者是初版的错，后者是回声不是记忆。

## 10. 需要 owner 拍的四件事

1. **T05 输出契约必填 `memory`**——一次响应必须对"有没有值得记的东西"表态。这是模型面的输出契约变更。
2. **T07 放宽指令不变量**——允许"同时调用能力并回复"。
3. **T08 写入去重**——命中重复时返回 `duplicate: true` 而不新建 revision。
4. **T04 定性**——并发 attach 的失败，是测试写窄了，还是 store 把可重试冲突映射成了不可重试错误。

前两件决定 S2 能不能一次做完；第三件必须同批；第四件可以并行。
